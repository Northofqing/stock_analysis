## 2. 事故：monitor 停摆 46 分钟（08:14 → 09:00）

### 2.1 发现

用户 08:48 提「监控 monitor」。实测 `pgrep -fl release/monitor` **为空**，ps 里只剩 Sep 19 起的
`grpc_market_server`。距集合竞价 27 分钟。

最后活动：stderr `08:14:02`、DB WAL `08:14:12`、stdout 心跳 `07:55:29`（每 ~31 min 一次，**08:26 那次缺失**）。

### 2.2 死因（证据链，已坐实）

| 证据 | 值 |
| --- | --- |
| 崩溃证据 | **无 panic、无 crash report、无 jetsam、无内存压力** |
| 启动它的会话 | `8d0f777b`，transcript 内可查到它在 **21:06:33** 经 Bash 工具启动 monitor |
| 该 transcript mtime | **08:14:06** |
| monitor 最后活动 | stderr 08:14:02 / DB WAL **08:14:12** |
| 该 transcript 最后**对话内容** | 停在 9/22 23:25，之后 9 小时无内容却被再次写入 |

⇒ **该 agent 会话进程退出时对子进程做进程组 teardown（SIGKILL），把 monitor 一起带走了。**
transcript 在 9 小时空白后被再次写入 = 进程退出时的最终 flush；与 monitor 死亡重叠在 6 秒内。

**关键机理**：`nohup` 只忽略 `SIGHUP`，**挡不住进程组 SIGKILL**。所以「launchd 损坏 → nohup 直跑」
这套沿用已久的 workaround，其**寿命上限 = 启动它的那个 agent 会话进程的寿命**。会话活一夜，
monitor 就活一夜；会话一关立刻死，且死得没有任何崩溃痕迹 —— 极易被误判成「Mac 睡眠」或「上游抖动」。

### 2.3 为什么没有自动恢复（比死因更值得记）

`~/Library/LaunchAgents/com.stockanalysis.monitor.plist` **一直存在且带 `KeepAlive=true`**，
但 job **从未被 load**（`launchctl print` → `Could not find service`），CronList 为空。
⇒ 死了就是死了，没有任何机制接管。

根因是一段**错误前提的固化**（详见 §5）。

## 6. 本段新发现的陷阱（已写入记忆）

1. **生产进程不能是 agent 会话的后代** → 记忆 `agent-session-child-process-lifetime`。
   判据速查：**无 crash report + 无 jetsam + 最后日志正常 ⇒ 外部 SIGKILL，别去查上游**。
   排查「进程静默消失」的第一个工件是**启动它的那个 agent 会话 transcript 的 mtime**
   （`~/.claude/projects/<proj>/*.jsonl`），**不是** `logs/monitor.log`（无日期前缀，跨天骗人）。
2. **「被 gitignore 但已跟踪」是本仓库的常态，改这类文件一律要 `git add -f`**：
   - `config/`（`.gitignore:13` 的 `/config`）— 但 `selection_activation.v1.json` 是跟踪的
   - `docs/session-handoffs/` — **本段写这份交接时又绊了一次**（首次 `git add` 被拒）
   坑点：`git check-ignore` **默认跳过已跟踪文件**，所以查它不报错，但 `git add` 会拒。
   判据用 `git ls-files <path>`（有输出=已跟踪），不要用 `check-ignore`。
3. **hash 失配是重启的隐性拦路虎**：任何 supervisor 之外的 src 改动都会让 activation 失效，
   而失效表现为「进程正常起来、selection 与新闻静默关闭」，**不报错**。
   重启前必做 `print-activation` 对hash（本段即靠此拦下）。
