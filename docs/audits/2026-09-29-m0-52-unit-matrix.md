## 可复现的 52 Unit 对账方法

1. 固定三个身份层：`git rev-parse HEAD` 与 v1/delta SHA；运行 PID 对应 binary、公开 bundle/activation 哈希；远端 VM Health + descriptor/source revision（只在已有只读窗口取）。每份样本带 CST 时间、business date、source revision 和运行 PID，禁止把隔离树代码或探针结果当成旧生产进程。
2. 以 v1 的 `(unit.id, producer_ids, occurrence_families, completion_owner)` 生成下表；以 v2 kind delta 覆盖 `news-ai-same-tick` 的当前 kind，不改写 v1。逐 producer 按工作表 `trigger/source/authority/policy/evidence_ids` 找当前函数和 caller；`rg -n 'producer 或 kind 符号' src/bin/monitor src/push_foundation src/database` 仅是定位，必须沿真实调度入口、source、send、失败推进和恢复路径读通。enum 外 CLI/timer 保持独立 Unit。
3. 每 Unit 建一行样本键：`business_date + occurrence_identity + producer_id + physical_owner + source batch/assessment hash + decision_identity + attempt_identity + sink result identity + business cursor/intent state`。共享 Unit 的多个 producer 必须一起核原子边界；同 kind 的多入口按 occurrence 区分。对 legacy L4/bool、文件或内存门，若无 durable decision，明确记 `无 durable decision`，不能编造 JOIN。
4. 对 counted 路径先做只读聚合识别候选，再在授权的受控审计窗口按 hash/opaque ID 对单笔关联，不输出 `envelope_canonical`、`result_canonical`、正文、证券/账户或凭据。确认 `Accepted` 权威性、渠道要求、platform receipt，再核业务 DB 的 exact finalizer/cursor CAS 或 review task hydration。对 generic/CLI/timer 单列实际外部渠道收据与业务完成证明。`Uncertain` 只由独立渠道证据和人工裁定推进。
5. 每 Unit 的证据等级分开填写：`Source wired`、`deployed binary`、`real source admitted`、`durable/transport accepted`、`external receipt`、`business finalized`、`restart/retry observed`。只有同一 occurrence 串起这些层且故障矩阵无双发/超龄 finalizer，才可讨论 Production Verified；禁用、Starved、Opt-in 以预定门禁状态验收，不靠伪造送达。

## 只读复查命令与窄查询

在隔离树根执行目录检查；运行库查询采用绝对路径，`-readonly` 与 `query_only=ON` 双重限制。输出仅为聚合；不要选择 canonical BLOB 或原始 message ID。

```sh
python3 scripts/push_catalog_drift.py
shasum -a 256 docs/push-system/push-capability-catalog.v1.json
sqlite3 -readonly /Users/zhangzhen/.local/share/stock-analysis-runtime/data/durable_delivery.sqlite3 "PRAGMA query_only=ON; SELECT state,COUNT(*) FROM delivery_decisions GROUP BY state ORDER BY state;"
sqlite3 -readonly /Users/zhangzhen/.local/share/stock-analysis-runtime/data/durable_delivery.sqlite3 "PRAGMA query_only=ON; SELECT d.push_kind,d.state,COUNT(DISTINCT d.decision_identity) decisions,COUNT(DISTINCT CASE WHEN s.result_kind='Accepted' AND s.authoritative_for_state=1 THEN s.result_event_identity END) authoritative_accepted FROM delivery_decisions d LEFT JOIN sink_results s ON s.decision_identity=d.decision_identity WHERE d.business_date='2026-09-28' GROUP BY d.push_kind,d.state ORDER BY d.push_kind,d.state;"
sqlite3 -readonly /Users/zhangzhen/.local/share/stock-analysis-runtime/data/durable_delivery.sqlite3 "PRAGMA query_only=ON; SELECT d.business_date,d.push_kind,COUNT(DISTINCT d.decision_identity) decisions,COUNT(DISTINCT CASE WHEN s.result_kind='Uncertain' THEN s.result_event_identity END) uncertain_results,SUM(CASE WHEN s.result_kind='Uncertain' AND s.channel IS NULL AND s.provider IS NULL AND s.message_id IS NULL AND s.platform_message_id IS NULL AND s.delivery_audit_ref IS NULL THEN 1 ELSE 0 END) missing_external_identity FROM delivery_decisions d LEFT JOIN sink_results s ON s.decision_identity=d.decision_identity WHERE d.state='UncertainManualReview' GROUP BY d.business_date,d.push_kind ORDER BY d.business_date,d.push_kind;"
```

查询结果只是候选索引。`COUNT(DISTINCT decision_identity)` 防止多 sink result 扩大 decision 数；权威 Accepted 数仍需同一 decision 的唯一性、要求渠道和业务 finalizer 逐笔核验。生产库持续写入时两次查询不构成原子快照，比较前需记录采样时间与水位。
